### V02 / P0：重复执行使新约束失效

以下是源码路径确认；当前服务不能导入，因此不冒充已经完成 HTTP 实测：

- `server.py:156`、`:293` 等同一分支两次输出 JSON；健康接口先输出旧响应，新增 `libraryInstanceId` 不能可靠到达调用方。
- `server.py:566` 保存复核页后继续命中新路由，以相同 `baseRevision` 再保存。第一次已创建草稿，第二次将产生版本冲突。
- `server.py:509` 先无条件交卷，再调用带 `expectedResponseVersion` 的新逻辑；`sessions.py:230` 发现已有结果会直接返回。因此第一次操作已经绕过新加的交卷版本检查。
- 最终快照的 app.js 已改为只发送带版本交卷，但服务端旧入口仍在，前端修复不足以解决服务端绕过。
- `server.py:526` 先按 cwd 写清单，再按 workspace 写清单；跨工作目录隔离仍未落实。
- `sessions.py:263` 附近同一次提交追加两次 SUBMIT 事件，后续按事件汇总会重复计数。

修复条件：每条请求只有一个业务入口和一个响应；交卷前在同一事务检查已确认版本；检查额外路径片段、重复请求和跨 cwd 写入。

### V03 / P1：草稿实例身份仍不持久化，保存恢复需整体验收

初查独立复现的 API 409 丢失错误码、新格式草稿返回 null、提前删除 pending 导致 base 不更新，在后续文件变动中已有修正。中间复查确认独立 API 函数返回 status=409/code=SESSION_CONFLICT，新格式草稿读取成功。不能继续把这三个反例写成仍然失败。

仍存在：`server.py:765` 每次启动随机生成 instance_id；重启改变同一题库的新草稿键空间。健康接口还先输出不含实例 ID 的旧响应。多标签页、慢请求、未确认草稿、重启的完整回归仍被服务启动失败阻断。

修复条件：持久化题库实例 ID；单一健康响应；验证不同题自动合并、同题选择、响应丢失、旧键迁移及服务重启。

对应：R04/R09、U03/U04、IMP-08。
