# 正确 pipeline 的补完与 EJU 制作工作台（2026-09-10）

前置阅读：[内容真实性记录](CONTENT_INTEGRITY_2026-09-10.md) 说明了旧脚本编造题面与答案的问题，
以及本轮建成的提取链。本文记录**把提取链接回复核签署流程**这一步，以及驱动它的工作台。

## 1. 之前缺的是什么

提取链能产出可验证的内容，但它把成品直接写进题库：

```
OCR → 组卷 → db.publish()          ← 绕过复核，与旧脚本同一个毛病
```

后果是 `page_revisions` 只有 1 条、`source_structure_revisions` 0 条、`paper_reviews` 0 条——
**前端重构出来的八阶段复核台根本没有东西可复核**（216 个来源里只有 1 个有页面合同）。

正确的形状是：

```
OCR → 页面合同草稿 → 复核台（人逐页核对并签署）
    → 签署来源结构 → 确定性 assembler 组装 → 签署整卷 → 发布
```

## 2. 页面合同：补上的缺环

`eju_bank/ocr/page_contracts.py` 把 OCR 读到的内容写成 `work/<来源>/pages/pNNNN-<role>.json`，
也就是复核台读、编辑、签署的那个文件。

草稿被**刻意做成签不了的**：

- 带 `needsReview`，`sign_page` 见到就拒绝；
- `issues` 逐条写明还差什么人来确认，首要是**区域证据**。

区域证据为什么必须由人给：签署闸门要求「每个来源区域恰好对应一个内容块的处置」
（`coverage.regionIds` 与各块 `regionIds` 集合相等）。PROBE 只给页级统计
（`imageBlocks` 计数、`inkRatio`），**没有区域 ID**；OCR 读文字，不读页面几何。
所以草稿绝不预填 `regionIds`——伪造它就等于让机器替人签字。

实测（`2002-1-japanese`，52 页）：

```
OCR_CONTRACTS → {'pages': 52, 'written': 52, 'questions': 20, 'verifiedAnswers': 128}
p0033: 問1 answerRef=READING:1 notes="正解表 READING:1 = 1" needsReview=True
复核台 read_page → 可读；save_page → 可存
sign_page → 拒绝："Resolve all contract issues before signing"
```

## 3. 三个新任务类型

OCR 挂进了项目已有的任务队列（lease／心跳／进度／取消／断点续跑），所以工作台能看到实时进展：

| 任务 | 做什么 |
|---|---|
| `OCR_TEXT` | 题册逐页转写；答案册同时取纯文本与表格两种读法 |
| `OCR_SLOTS` | 裁右边距读方框里的解答欄号——与正解表对接的键 |
| `OCR_CONTRACTS` | 生成页面合同草稿；顺带报告本回次可用的已验证答案数 |

三步都跳过已完成的页，`force` 才重跑。视觉服务地址被限制在回环接口：
让页面指定任意地址等于把原页图发到外部。

代码抽成了可复用模块，避免脚本与服务两处逻辑漂移：

- `eju_bank/ocr/local_vision.py`——调用本机视觉服务，不在进程内再加载模型
- `eju_bank/ocr/verified_answers.py`——答案加载（同回次共享正解表），脚本与 worker 共用一份

## 4. 数学接入（86 个来源）

数学是数字格、一問多欄，与选择题形状不同，走独立路径。

**对接依据是欄位字母**：正解表印 `ABCD 5723`（A=5,B=7,C=2,D=3），题册的题干里印
`\frac{J}{KL}`。欄位从**正解表**取（权威），题干里无歧义出现的字母（只认 `\boxed{}`
与 `\frac{}{}`）用来**交叉校验**——因为题干里的裸大写字母同样可能是变量名或大題编号。

实测 `2015-1-math-c1`：6/6 全出，含两个无「問N」的大題（第III問、第IV問），
欄位数 9/12/14/12/12/15 与正解表逐一吻合。`2015-1-math-c2` 出 3 题，
1 题因题干字母与正解表不符被拒——保护生效。

全语料：**86 个数学来源中 54 个有产出，共 256 道**。加上其他科目，
带已验证答案的真题从 1745 升到 **2001 道**。

接进发布路径时还修了两处：`build_math` 一开始定义了却没人调用（数学来源在发布路径上
拿不到 OCR 题目）；闸门里留着「数字格暂不接受」的一刀切，而且判断顺序让 `answer is None`
先命中，数字格分支永远走不到。现在数字格按**来源标记**放行——`build_math` 给它产出的题
打上 `_answerSource: answer-key`，闸门核对标记在、且逐格答案正好覆盖该题欄位，发布前摘掉标记。
这样「只有来自答案册的答案能存活」这条不变量在一处可查。

沿途修掉三个会**写错答案**的问题：

- **問号未随大題重置。**III、IV 整题只有一组欄位、不带「問N」，却继承了上一个大題的「問2」，
  被错标成「III 問2」——等于把欄位安到别的題上。
- **罗马数字与欄位字母同形。**`I 2` 是「欄位 I = 2」，被当成大題 I。判据：行首若能直接
  解析成「字母 数字」，它是数据行。
- **题册 PDF 末尾附印了正解表。**那些页被当成题干读，造出三个重复的「IV 問2」，
  撞掉审计的唯一性检查。现在按标题与行密度识别并跳过，并对重复的 (大題,問) 去重。

## 5. 下架未经验证的卷

`scripts/retire_unverified_papers.py`。判据两条：选项是字面占位符，或者没有复核证书。

用的是项目自己的机制 `set_delivery_state(..., 'SUSPENDED')`：版本、内容与学习记录全部保留，
只是不再提供新练习。可逆——签署通过后置为 `REVIEWED` 即可重新开放。

执行结果（快照已存于 `../eju-db-before-retire-*.db`）：

```
占位内容（题干模板 + 选项占位 + 编造答案）: 126 套
无复核签署（内容可能真实，但没人签过字）  : 91 套
保持开放                                  : 0 套
→ 已停止新练习 217 套 · 清单纠正 215 条 PUBLISHED → RECEIVED
```

数据保全核对：7197 题、20247 个题目版本、59 次练习会话、57 条错题记录，一条未删。
`list_papers` 仍返回 217 套，可练 0 套，每套都带明确的停投放原因。

**题库因此暂时没有可练的卷**——这是真实状态。任何一套走完复核签署即可重新开放。

三个依赖正式库的测试原本断言「在占位卷上能练习」，已改为断言受限投放会被拒绝
（`test_review_content_workflow` 等），并保留原本的解析装配覆盖。

## 6. 工作台

`start/eju_studio.py`（另有 `eju-studio.sh`），形态对齐 `start/dictation_studio.py`：

```bash
python eju_studio.py                 # 起服务并打开 http://127.0.0.1:8765/studio
python eju_studio.py --no-browser
python eju_studio.py --port 8800
EJU_WORKSPACE=/abs/path python eju_studio.py
```

与练题界面同一个服务、同一个数据库，但界面和进度口径分开：制作台管"这套卷做到哪一步
了"，学习页面管"我练到哪了"。本机访问不需要任何口令。

阶段 ④ 里加了「本地 OCR」三步，用有序列表而不是并排按钮——顺序即依赖。任务卡显示实时
进度、可取消。「重跑已完成的页」是个显式勾选项，默认跳过：否则一次误点要重跑几千页。
