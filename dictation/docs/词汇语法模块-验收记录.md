## 4. 查询性能实测

本机（Python 3.11，JMdict 218,726 词目，491 条内容索引条目），200 次混合查询：

| 个人卡片规模 | 冷启动 | 中位 | p95 | 最大 |
|---:|---:|---:|---:|---:|
| 1,000 | 262.7 ms | 10.4 ms | 16.9 ms | 27.0 ms |
| 5,000 | 293.2 ms | 46.2 ms | 50.7 ms | 74.4 ms |
| 10,000 | 236.6 ms | 94.0 ms | 96.3 ms | 97.8 ms |

热查询 p95 远低于文档建议的 300 ms 目标。**但要注意增长是线性的**：个人条目来源目前是
全表扫描后在内存里过滤，10k 卡片已是 94 ms 中位，约 30k 就会接近目标上限。真要支撑更大
规模，个人条目需要和教材一样进可查询索引；这不在本轮范围内。

## 5. 补做：顺序学习流程

原来「今日背诵」只显示**计划已投放且已到期**的卡，所以没有计划时永远是空的；而单元视图上
的「学习本单元」其实跳转到**建计划表单**。结果是：要通读一个单元的 22 条，只能一条条点详情。
浏览、计划、练习都有，唯独没有「学习」。

新增：

- 服务端 `POST /api/lexicon/introduce`（`LexiconLearning.introduce()` +
  `LearningStore.introduce_cards()`）：把选定条目按选定方向直接建成复习卡。方向经 §4.2 的
  同一适配器解析，所以顺序学习建的卡与计划投放的卡是**同一张**；墓碑照旧避让，重复学习
  不会重置进度；条目在该方向上无法出卡时按 `no-direction` 报告而不是静默少建。
- 前端 `#/learn/<slug>[/<unitId>]` 视图：进度（已处理 / 已加入复习 / 剩余）、完整条目内容、
  可选「先遮住释义自测」、逐条「加入复习」或「已会，跳过」、收藏 / 笔记 / 朗读 / 看详情 /
  上一条，键盘 1・2・←・→・空格。进度写入 IndexedDB，关掉再回来从原处继续。
- 入口：单元的「开始学习本单元」（主按钮）、内容包的「学习整个内容包」、空的今日背诵页
  「去学一个单元」。原来的按钮改名为「加入学习计划」，详情页的「加入学习」拆成
  「加入复习」（真的加入）与「加入学习计划」。

覆盖：`tests/test_lexicon_learn.py`（14 项，含 HTTP 层）。实测：`u2 饮料` 13 条走一遍，
加入 10 条、跳过 3 条，今日背诵随即出现 10 张到期卡，**一个计划都没建**。

## 6. 一次真实故障与它带来的检查

第一版交付后页面是**空壳**：`restoreScope()` 与 `describeScope()` 被调用，但它们的定义在
一个中途失败的批量补丁里丢了（补丁脚本只在最后写盘，一处匹配失败就丢弃全部修改，而我
随后只补回了调用侧）。init 一抛 `ReferenceError`，整页什么都不渲染。

单元测试和 `node --check` 都发现不了这个：语法是合法的，而没有任何测试执行页面的 init。
新增 `tests/web_symbols.test.mjs` 补这个缺口——它剥掉注释、字符串与正则字面量后扫描调用
点，再对照每个页面按 HTML 顺序加载的脚本所声明的符号。已验证把 `restoreScope` 的定义删掉
它就会失败。同时检查 SW 的 `SHELL_ASSETS` 覆盖每个页面加载的脚本（缓存里缺一个脚本，等于
离线时 init 必抛）。`SHELL_CACHE` 也已从 v44 升到 v45，因为资源清单变了。

教训与做法：批量补丁必须逐处校验、失败即止并检查落盘结果；改前端必须至少有一道能捕获
「调用了不存在的东西」的自动检查。
