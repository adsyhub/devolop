不在本文件手写。

## ADR-BUILD-001 —— 工具链与 artifact 策略

**状态**：已签署（2026-08-20）

**决定**

| 项 | 选择 |
|---|---|
| Python 版本 | 3.13（实测运行版本，见事实文件） |
| Python 测试运行器 | 标准库 `unittest` |
| JavaScript 测试运行器 | `node:test`（Node 24） |
| 唯一测试入口 | `python run_tests.py` |
| 前端构建器 | 不引入 |
| 浏览器 E2E | **待定**（见下方「未决」） |

**理由**

播放器本身只依赖 Python 标准库，这是这个项目的核心性质：拿到目录就能跑，不需要
安装步骤。为测试引入 pytest 会让测试套件成为整个项目里唯一需要 `pip install` 的
部分，收益（fixture 语法更短）不足以抵消这个代价。方案原文允许 unittest，只要求
「只保留一种主入口」，这一条由 `run_tests.py` 满足。

Service Worker 的缓存与 Range 逻辑无法用 Python 测试，因此 JavaScript 侧必需，
选 `node:test` 是因为它随 Node 分发，同样不需要装依赖。`run_tests.py` 在 Node
缺失时**报错而非跳过**——静默跳过唯一覆盖缓存与 Range 的测试，正是这个项目当初
测试归零的方式。

**artifact 策略**

大文件不入 git，改由 SHA-256 清单索引：

- `*.mp3`、`dist/*.zip`、`.codex_qa/rendered/` 已在 `.gitignore` 中排除。
- 哈希清单由 `python src/snapshot_evidence.py` 生成，快照本体（含学习数据库）落在
  `assets/snapshots/`（不入库），清单副本落在 `assets/evidence/`（入库）。
- 取回方式：课程音频与 ZIP 目前只存在于本机与 OneDrive；清单记录了字节数与
  SHA-256，可用于验证任何一份副本是否就是当初那一份。

## ADR-MODEL-001 —— 模型是运行时配置，不是源码常量

**状态**：已签署（2026-08-31）

**决定**

构建流水线不内置任何模型名。ASR 与文本生成都通过 *provider* 抽象，由
`config/providers.json`、环境变量和命令行参数在运行时解析（后者覆盖前者）。
网络类 provider 解析不出模型名是**启动期错误**。

| 项 | 选择 |
|---|---|
| 文本 provider kind | `openai-compat` / `anthropic` / `ollama` / `cli` / `manual` / `echo` |
| ASR provider kind | `faster-whisper` / `openai-audio` / `command` / `import` |
| 传输层 | 标准库 `urllib` 与 `subprocess`，不引入任何厂商 SDK |
| 密钥存放 | 配置里只写**环境变量名**（`apiKeyEnv`）；字面量密钥拒绝加载 |
| 默认模型 | **无**。缺模型时报错并列出三种设置方式 |

**理由**

此前 `deepseek-v4-flash` 与 `large-v3` 是模块常量。三个后果：

1. 「这门课是哪个模型做的」是源文件的属性，不是构建的属性——课程本身答不出来；
2. 模型名下线后，构建要跑到第一个批次才失败，此时音频已经转写完；
3. 转写写死 CUDA + float16，没有 NVIDIA GPU 的机器根本无法构建课程。

改为运行时解析后，换云端 API、换本机模型、换成已订阅的 AI CLI，或者直接导入外部
转写，都是命令行改动而不是代码改动。每次构建把解析结果记进
`buildMetadata.asr` 与 `buildMetadata.enrichment`，课程从此带着自己的来历。

**为什么保留 `cli` 和 `manual` 两种「不像 API」的 provider**

订阅席位不是 API key，但它是一个能回答提示词的进程；`cli` 承认这一点。`manual`
连进程都不要求：写出提示词文件，人在任意聊天窗口里回答后存回来。这两条是没有
API 预算时唯一能把课做完的路径，不是玩具。

**为什么 `echo` 的产物默认不许打包**

`echo` 写的是可见占位符。占位符能让课程通过「有 explanationText」这类检查，于是
一份没有任何模型或人写过的文本会摆在学习者面前——这正是这个项目已经栽过一次的
损坏内容问题。因此打包需要显式 `--allow-stub-enrichment`，且产物被标记为
`review.humanListening = "blocked"`。

**兼容性**

`src/build_deepseek_offline_bundle.py` 保留为薄兼容层：它仍向九个模块再导出
`load_json` / `write_json` / `sha256_file` / `build_zip` / `verify_zip`（实体已移入
`src/bundle_io.py`），并把旧参数翻译到新流水线。唯一不能保留的行为是那个写死的
默认模型——`--deepseek-model` 现在必填，把失败从第一个批次提前到启动。

## ADR-CONTENT-001 —— P0 学习键与 alias 合同

**状态**：部分签署（2026-08-20）。alias 表已生成，**内容切换尚未批准**。

**已决定**

- P0 阶段学习键固定为 `(courseId, sentences[].id)`，即 v1 manifest 的原样字段。
  现 review/API 中的 `sentenceId` 视为同一个值的另一种命名。
- 听审质量（`review.humanListening`）与分发权利（`review.commercialRights`）是
  两个独立状态，任何一方通过都不得推断另一方。
- alias 表必须绑定源/目标 `contentRevision`。未绑定 revision 的 alias 表等同于
  静默数据损坏，禁止使用。

**已生成的证据**（`assets/content_candidates/2010-12-N2/`）

| 项 | 数值 |
|---|---|
| 音频是否同一份 | 是（SHA-256 一致） |
| 段数 | 629 → 517 |
| 可练习段数 | 457 → 431 |
| 句子 ID 交集 | **0** |
| 精确匹配 | 381 |
| 建议匹配（需人工确认） | 68 |
| 歧义 | 0 |
| 无法匹配 | 180（其中 77 段可练习） |
| 仅候选包中存在 | 68 |
| 候选包音频覆盖变化 | **−285 秒**，空洞 +60 |

**尚未决定，因此不切换默认课程**

1. 候选包的听审状态仍为 `pending`，按合同只能称「技术候选」，不能称 canonical。
2. 候选包少覆盖 285 秒音频、多出 60 处空洞。它的「0 错误」有一部分不是修好了，
   而是**内容变少了**。在解释清楚这 285 秒去了哪里之前，切换等于用静默的内容
   缺失换取好看的审计数字。
3. 180 段无法匹配意味着这些段上的进度、笔记与生词在切换后会成为孤儿。

**下一步**：先解释 285 秒差异，再做逐句听审，两者都通过后才讨论提升为 canonical。

## ADR-STORE-001 —— 浏览器与 SQLite 的职责

**状态**：**未签署**。长期权威存储与跨 profile 对账方案仍不得在签署前定型。

方案推荐的方向是「IndexedDB 为单个浏览器 profile 的离线权威，SQLite 为在线时按
profileId 隔离的备份/恢复副本」。当前只落地了不预设最终权威归属的安全子集：固定 origin、
基于 `localStorage` 的持久化 outbox、删除墓碑、顺序重放，以及服务端写入幂等。它解决断网
编辑丢失、旧快照复活和重复重放副作用，但不是 IndexedDB 迁移，也不处理跨 profile 合并。
如果团队改选「双主」或「Python companion 必需」，DAT-001/DAT-002 的工期与设计仍要重估。

**当前真实状态**：进度与 outbox 仍在当前浏览器 profile 的 `localStorage`；生词、笔记、
打卡、学习日志和 SRS 复习会先本地生效，联网后重放，并在启动时合并本地与服务端快照。
单 profile 的离线可靠性缺口已缓解；浏览器数据被清除、跨 profile 合并和最终权威存储选择
仍未解决。

## ADR-PWA-001 —— 媒体缓存粒度与更新协议

**状态**：部分签署（2026-08-20）

**已决定**

- 课程 manifest 是**指针**不是资产，采用网络优先、离线回退。
- 课程缓存采用「暂存 → 逐项校验 → 发布指针 → 删旧」的可恢复两阶段切换。
  这不是跨存储原子操作（Cache Storage 与注册表是两个存储，无法放进一个事务），
  但每一个中断点都留下可用状态，这才是实际需要的性质。
- 应用壳缓存名带版本（`dictation-shell-v9`），激活时清理旧版本。

**未决定**

- **音频存储粒度**：整文件 / 分块 / 句级。当前实现是整文件 + 流式 Range 读取：
  只保留请求的片段，不再把 21.5MB 读成单个 ArrayBuffer，但仍需从流头读到
  range 起点。分块存储可以完全消除这段跳读，代价是打包与缓存管理复杂度。
  方案要求先做性能 spike 再定，因此这里**没有**提前实现分块。
- **内存门限的实测阈值**：方案给的初始验收是「1MiB range 单次增量 heap ≤8MiB」。
  当前只有单元测试证明「读取字节数远小于全文件」，没有真实浏览器 heap 实测。

## ADR-EXAM-001 —— JLPT 题库与听写播放器同进程、同存储

**状态**：已签署（2026-08-31）

**决定**

| 项 | 选择 |
|---|---|
| 部署形态 | 与播放器同一进程、同一端口、同一 `SecurityContext` |
| 作答记录 | 写进播放器已有的 `learning.sqlite3`，不新建数据库 |
| 页面 | 独立页面 `/exam.html`，不塞进 `app.js` |
| 正确答案 | 随卷子一起发到浏览器；由界面而非网络控制何时可见 |
| 内容质量 | 审计有错误的卷子拒绝提供（HTTP 422），与课程 fail-closed 一致 |
| 计分 | 按本次练习范围计分，不按整卷 |

**理由**

**同进程**。题库需要的一切播放器都已经有了：回环授权、会话令牌、静态服务、
Service Worker、SQLite。另起一个服务意味着第二个端口、第二套令牌、第二份备份说明，
以及「生词本在这边、错题本在那边」的割裂。代价是 `serve_course.py` 多了三行路由分发。

**同存储**。学习者的错题本和生词本是同一件事的两面——都是「我还没掌握什么」。放进
同一个文件，快照、备份和 `snapshot_evidence.py` 都不用改。

**独立页面**。`app.js` 已经 97 KB 且状态密集（音频、波形、字幕、进度同步）。把答题
流程塞进去会让两个功能互相牵连，而它们之间唯一真正共享的是设计变量和授权握手，两者
都能靠 `app.css` 和 `/api/session/bootstrap` 复用。风险不对称：改坏播放器的代价远大于
少复用几个函数的收益。

**答案随卷子下发**。藏起来是做样子：这是单机自学工具，进程是学习者自己的，
`app.js` 本来就把听写的正确答案发给了页面。真正的约束是离线可用——Service Worker
缓存卷子，一份判不了分的卷子不叫卷子。模考模式在**界面上**不显示答案直到交卷，
这才是有意义的那部分诚实。若将来要做「他人监考」的场景，再引入服务端判分。

**fail-closed**。答案表抄错一位，后面每一道题的答案都会串位，而学习者没有任何办法
发现——他会以为自己错了，然后把错答案背下来。这比「加载失败」严重得多，所以
`exam_import.py` 在数量对不上时直接报错停下，`audit_exam` 有错误的卷子服务端拒绝提供。

**按范围计分**。第一版按整卷计分，结果「只练問題1 且六题全对」在历史记录里显示成
4/176（2.3%）。这不是小数点问题，是把「练得很好」显示成「几乎全错」。所以开始作答时
客户端把题目集合发给服务端，交卷时只按这个集合计分。

**未决**

- 听力音频。当前 PDF 只有选项，題干与录音都没有；schema 里 `audioRequired` 已预留，
  接法留待拿到音频后再定。
- 尺度得点。答案表自己声明计分方式仅供参考，与官方 180 分制不一致；界面照搬了这句
  声明，没有假装能换算。真要给出接近官方的估分需要各级别的换算表，尚未取得。

## ADR-VIDEO-001 —— 在线视频课程

**状态**：已签署（2026-08-31）

**决定**

| 项 | 选择 | 被否决的方案 |
|---|---|---|
| 媒体如何记在清单里 | 新增 `media` 块，与 `audio` 二选一 | 复用 `audio` 存 URL |
| YouTube 如何控制 | 官方 IFrame Player API | 未公开的 postMessage 协议 |
| 站点能力差异 | 三档 `control`，UI 直说 | 一律当作可控 |
| 没有字幕时 | 临时取音频，`finally` 里删 | 缓存音频以便重建 |
| 逐句时间轴 | 视频绝对时间 | 相对 `clip` 的时间 |

**为什么 `media` 是新字段，不是重载 `audio`**

`audio` 在这个项目里有明确契约：ZIP 根目录下的安全文件名，会被复制进预览目录，
会被 Service Worker 缓存，会被 Range 请求分片读。往里塞一个 URL 意味着这四条
契约每一条都要长出一个 `if`，而 `safe_audio_name` 这类函数的名字会开始说谎。
二选一的代价是所有消费方都要判断一次，收益是每个分支的含义都还是它字面的意思。
「两个都有」是错误而不是可合并的状态：那是一个文件里的两门课，播放器无论选哪个，
另一半清单描述的都是学习者没在听的东西。

**为什么用官方 IFrame API，代价是什么**

YouTube 的 iframe 底下就是 postMessage，直接对着它发 `{"event":"command",...}`
可以完全不放宽 `script-src`。代价是这个协议没有文档、没有兼容承诺，一旦改动
是静默失效——播放器看起来正常，就是不动。这个功能的价值全在逐句精确循环上，
用一个随时可能无声失效的协议去承载它不划算。

因此接受 CSP 放宽：`script-src` 增加 `www.youtube.com` 与 `s.ytimg.com`。
这是真实的攻击面扩大，缓解措施是：只在播放器页面放宽（工作台的 CSP 未动）、
只加这两个域名、不加 `'unsafe-inline'`、`frame-ancestors 'none'` 保持不变、
三份 CSP 副本由测试守住一致性。

**为什么要有三档而不是假装都能控**

`seek-reload` 和 `external` 都是**残缺**的体验，把它们标成 `full` 会让 UI 出现
点了没反应的循环按钮。学习者会先怀疑自己的操作，再怀疑自己的耳朵，最后才怀疑
软件。宁可少给一个按钮，也不给一个骗人的按钮。

**为什么临时音频不缓存**

缓存它就等于在本地保存了一份媒体，那正是这个功能承诺不做的事。重建一次的代价
是再转写一次；把承诺换成一点速度不值得。删除放在 `finally`，异常路径同样删，
`.part` 残留一并清掉——只删「我们知道的那个文件」会在最需要干净的失败路径上留下
半个副本。

**为什么句子时间轴是绝对时间**

`clip` 只是「这门课覆盖视频的哪一段」。若把时间轴平移到相对 `clip`，那么构建器、
审计、播放器时间条、进度条和深链五处都要各自记得加回偏移量，少一处就是每次定位
都偏 `clip.startTime` 秒。绝对时间让 `clip` 退化成一个纯粹的过滤条件。

**未决**

- Vimeo 标为 `full`，但适配器目前只实现了 YouTube 的控制通道。Vimeo 的
  postMessage API 是有文档的，接上之前，Vimeo 课程实际会落到嵌入但不可控的行为。
  **这是已知的名不副实，需要在接入 Vimeo 适配器时消除。**
- 自动字幕质量没有量化门槛。目前只有滚动窗口去重，没有「这份字幕烂到不该做成课」
  的判据。
- 视频被删除或转为私享后，课程会静默失效。没有失效检测，也没有提示。

## ADR-LEX-001 —— 词与语法共用一套内容与调度

**状态**：已签署（2026-09-02，Phase A 落地）

**决定**

| 项 | 选择 | 被否决的方案 |
|---|---|---|
| 内容模型 | 一个顶层 schema，`kind: "word" \| "grammar"` 的 tagged union | 词汇、语法各一套 schema 与管线 |
| kind 专属字段 | 挂在 `word` / `grammar` 子对象里 | 顶层平铺，靠字段是否存在判断类型 |
| 卡片表 | 复用已有 `vocab` 表，不改名 | 新建 `lex_cards`，或把 `vocab` 重命名 |
| 到期口径 | 一个，词与语法同一队列 | 两个模块各报各的「今天要复习多少」 |
| 工作区 | 一个 `/lexicon`，三个视图 | 词汇、语法两个入口 |

**为什么是一套而不是两套**

一个词条是「見出し語＋読み＋品詞＋释义＋例句＋级别＋出处」，一个语法条目是
「文型＋接続＋释义＋例句＋级别＋出处」。差异是两个字段，共同点是全部：稳定 ID、
级别分组、多语种释义、来源追溯、搜索索引、SRS 调度、离线缓存、审计规则。

做成两个模块省不下代码，只会多出两套要各自维护的边界：两条导入管线、两条离线缓存
策略、两个「今天该复习多少」的口径。第三个尤其糟——学习者不需要知道自己欠了 40 个词
和 12 条语法，他需要知道今天要复习 52 条。

**为什么 `vocab` 不改名**

表名叫 `vocab` 而里面躺着语法条目，确实名不副实。但改名要动多处查询、幂等回执和每一个
已经存在的学习者数据库，收益只是好看。`entry_kind` 列承担实际区分，重命名留给未来的
大版本。

**代价**

`kind` 的分支散布在导入适配器、卡片模板生成和渲染里。这是显式的、可枚举的代价，比
两套边界各自漂移要好。

## ADR-LEX-002 —— 读音与释义的权威来源

**状态**：已签署（2026-09-02）；词典层部分在 Phase B 生效

**决定**

| 字段 | 谁负责 | 依据 |
|---|---|---|
| 表記 / 読み / 品詞 / 英文词典义项 | JMdict 记录（Phase B） | 开放词典，可核对、可署名 |
| 级别归属、教材顺序、中文/韩文释义、例句、接続 | 教材内容包 | 教材的编排本身就是教学内容 |
| 例句读音 | 只接受 `readingSource: dictionary \| manual` | 见下 |

`extract` 永远不写 `reading`；`prepare_pack()` 丢弃任何没有 `readingSource` 的读音；
`audit_pack()` 对来路不明的读音判 error。

**为什么 OCR 不能当词典用**

[docs/PDF_OCR.md](PDF_OCR.md) 已实测：默认分辨率下这本书的振り仮名字高约 12 px，
**模型看不清就会编读音**。要真读出来得 6.4 MP，整本约 14 小时且爆显存。

编出来的读音比不标读音更糟：不标读音时学习者知道自己得去查，标了错读音他会背下来，
而且没有任何界面能告诉他这条是编的。所以「没有读音」是一个要保留的事实，不是一个
要填上的空。

**匹配是四态的，不是二值的**

同形词、多読み、多义项和旧字体都可能让一个見出し語命中多个 `entSeq`。流水线保留
`matched / ambiguous / unmatched / manually-resolved`；`ambiguous` 与 `unmatched`
都是 fail-closed 信号。人工裁决写进独立的 `match-resolutions.json`，重跑不丢。

**范围边界**

可发布版本的中文释义来源与创作审核流程是另一个方案。当前教材私有包不得把它冒充
已经解决。

## ADR-LEX-003 —— 条目、卡片与计划的身份及修订协议

**状态**：已签署（2026-09-02，Phase A 落地）

**决定**

```
entryKey  在 entry-keys.json 中冻结，一次分配，永不重算
entryId   = kind[0] + "_" + sha256(packId + US + entryKey)[:24]     ← 96 bit
卡片身份   = source_ref + prompt_type + variant_key
计划       通过多对多表引用全局卡片，一张卡只有一份 SRS 状态
```

正文、`unitId`、`order` 一律不参与身份计算。`assemble` 遇到未注册的 `sourceAnchor`
只报告并失败；只有显式 `--accept-new-keys` 才分配新 key。

**为什么正文不能进 ID**

OCR 会改错字，条目会跨页拼接，补漏后单元顺序会变。这三件事都是「普通订正」，而把
見出し語或位置放进 ID 意味着每一次普通订正都会静默切断学习者的 SRS 历史——卡片还在，
只是不再指向那个条目，而界面无法显示这件事发生过。

**为什么是 96 bit**

与项目现有题库一致。6 个十六进制字符只有 24 bit：一个 2000 词的包至少发生一次碰撞的
概率约 11.23%，不可使用。

**为什么新 key 需要显式开关**

重新抽取会重新编块号，`pdf:18:block:3` 可能变成 `pdf:18:block:2`。若自动分配新 key，
一次抽取器改动就会给学习者已经背了一个月的条目发一批全新卡片。条目搬家的正确修法是
把已有 key 指向新 anchor——那是 `entry-keys.json` 里一行可审查的 diff。

**修订协议**

- 身份未变：刷新卡片快照，保留全部 SRS 字段；
- 条目重排：只改 `ordinal`；
- 确实拆分/合并/删除：走显式 `idAliases` / retired 迁移，禁止删除重建。

## ADR-LEX-004 —— 长期复习、成熟与暂停

**状态**：已签署（2026-09-02）；迁移在 Phase C 执行

**决定**

- `srs_stage = 3` 表示**成熟**，仍按 `next_review_at` 进入复习队列；
- 新增 `review_suspended` 表示学习者主动移出复习，调度器不得自动写它；
- 只有 `review_suspended` 排除到期队列，`mastered` 不再参与 due 查询；
- `grade` 只接受 `again / hard / good / easy`，其他值返回 400 且状态不变；
- Python 与浏览器各一份纯函数 `schedule(state, grade, reviewed_at_utc)`，不读系统时钟，
  共用固定时间的 JSON 测试向量。

**为什么必须先改语义再接新卡**

现状是：调度器进入 `srs_stage = 3` 后自动写 `mastered = 1`
（[local_backend.py:590](../src/local_backend.py#L590)），而 `/api/review/due` 又排除
`mastered`（[local_backend.py:428](../src/local_backend.py#L428)）。成熟卡因此**永远不会
再次到期**。把 N1–N5 的词汇接到这套语义上，等于承诺一件它做不到的事：长期保持。

**迁移的取舍**

旧 `mastered` 行分两类：

- `mastered = 1 AND last_reviewed_at = ''` 可判为人工勾选，回填为暂停；
- 有复习时间的行无法区分「自动成熟」和「复习后人工勾选」。

产品决策是**恢复按 `next_review_at` 到期**，同时把 ID 写入迁移报告，在个人中心提供
一次性批量重新暂停。不能把旧 `mastered` 全量回填为暂停——那只是换了个字段名，自动成熟
卡仍会永久消失，也就是这条 ADR 要修的那个 bug。迁移前备份，允许按快照回滚。

## ADR-LEX-005 —— 浏览器个人卡片存储

**状态**：已签署（2026-09-02）；实施在 Phase C

**决定**

| 数据 | 存放 | 理由 |
|---|---|---|
| 卡片快照 + SRS 本地副本 | IndexedDB，按 `vocab.id` | 体积大、结构化、异步 |
| 评分 mutation outbox、删除墓碑 | 继续留 localStorage | 小、关键、依赖同步写入与既有顺序 |

旧生词在首次升级时以单事务导入 IndexedDB，成功后才删旧键；配额失败时停止批量投卡并
保留旧数据。

**为什么不继续用 localStorage**

N1–N5 的多语言例句加多 variant 卡片会稳定超过 localStorage 的合理容量（通常 5 MB），
而且它的 JSON 序列化是同步的，会在投卡时阻塞页面。

**为什么 outbox 不一起搬**

outbox 与墓碑体积极小，但它们的正确性依赖「写入立即生效」和现有的顺序重放语义。把它们
改成异步 API 要重做那套顺序保证，换来的容量收益接近零。

## ADR-LEX-006 —— 教材内容包的版本库与发布边界

**状态**：已签署（2026-09-02，Phase A 落地）

**决定**

1. `sourceType: textbook-ocr` 时 `attribution.redistributable` 只能显式为 `false`；
   `prepare_pack()` 遇到其他值直接失败，不静默改写。
2. `audit_pack()` 对声称可分发的教材包判 error（`pack.redistributable_claim`）。
3. 通用 `src/distribution_policy.py` 判定边界，由 `release_readiness.py` 调用；
   **只扫制品，不扫工作树**。
4. `.gitignore` 排除 `lexicon/*/pages/`、`pack.json`、`units.txt`、`match-report.json`、
   `match-resolutions.json`。进库的只有 `pack-meta.json`、`source.pdf.sha256` 和
   **不含正文/词典 ID** 的 `entry-keys.json`，由 `audit_entry_key_registry()` 在写入前
   和测试中各扫一次。

**为什么改写权利声明比报错更糟**

把 `true` 静默改成 `false` 会掩盖一件事：这个包是在「以为可以分发」的前提下做出来的。
下一个人读到的是改正后的文件，不是那个误解。报错让误解留在原地被看见。

**为什么只扫制品不扫工作树**

开发者机器上有从自己买的书做出来的包，这是正常的。要防的是其中一份被复制进会被公开的
东西里。扫工作树会让每一次 release 检查都失败，而一个总是失败的检查等于没有检查。

**为什么不给 `make_zip.py` 加保护**

`make_zip.py` 和 `repack_offline_bundle.py` 只打单课程 ZIP，输入里本来就到不了
`lexicon/`。给一条不存在的路径加防护，读起来像有保护，实际什么也没保护住。等到它们的
输入被显式扩展时再加，那时保护才是真的。

**范围**

以上说明的是本项目的发布与版本库边界，不构成「自用必然合法」的法律结论。

## ADR-LEX-007 —— 复习目标、事件版本、审核状态与删除意图

**状态**：已签署（2026-09-07，B1 落地）

本条把 ADR-LEX-003 的「卡片身份 = source_ref + prompt_type + variant_key」补完到实际
存在的三条链路：计划发卡、专项练习、离线回放。在此之前三者各自造 ID，同一个能力会有
两份 SRS 状态。

**决定一：一个能力一张卡，三个身份分开**

```
reviewTarget  = {sourceRef, promptType, variantKey}   ← 长期 SRS 身份
questionId    = q_ + sha256(sourceRef + US + variantKey)[:24]  ← 练习题身份
answerVersion = sha256(判分内容)                      ← 答案版本
```

自动构造的题使用 `<promptType>-default` 作为题目 variant，`review_target()` 把它折叠
成计划卡的 `default`。因此 recall 与 production 的 **题目** 各自独立（否则 ID 相撞），
而它们的 **卡片** 分别是 `(ref, recall, default)` 与 `(ref, production, default)`——
与包里 `cardTemplates` 写的完全一致。cloze / usage 沿用模板自己的 variantKey，新增例句
生成新 variant，不按数组位置重编号。

不同题型不合并：读音方向与识义方向是两种记忆状态，合并会让「会读」冒充「会用」。

**为什么题目版本和答案版本必须分开**

改题面是普通订正，不该让已提交的答案失效；改答案集合必须让它失效。用一个哈希同时表达
两件事，只能二选一地错。

**决定二：`review_version` 而不是 `updated_at`**

只有调度类操作（评分、暂停/恢复、重置、删除/恢复、合并）推进 `review_version`。内容刷新
只动 `updated_at`。客户端评分带 `expectedReviewVersion`：

- 版本一致 → 推进，版本 +1；
- 版本落后 → 409，不推进；
- 同 operationId + 同请求摘要 → 返回原回执；
- 同 operationId + 不同目标或不同内容 → 409。

用 `updated_at` 做并发版本会让一次内容刷新把所有排队中的评分变成冲突——那不是并发保护，
是噪音。

**决定三：生成不是审核**

`draft → machine_checked → reviewed → withdrawn`。结构审计通过只到 `machine_checked`；
`reviewed` 必须有 reviewer 与覆盖当前内容的 `contentHash`。生成函数只能写
`machine_checked`。历史上的 `verified` 一律按 `machine_checked` 读取——它由生成器写入，
其证据里就写着 `notHumanReview: true`。

后果是明确的：两个包里 2,085 条自动模板暂时退出正式客观练习，`capabilities()` 按题型
返回 `available` 与 `reasonCodes`。这是本来就该有的账：把未审核内容计入「可用题量」，
等于用一个数字掩盖尚未做的工作。

**决定四：删除是意图，不是删行**

`lex_card_tombstones` 按 vocab_id 记录删除意图与版本。物理删行之后：

- `_materialize_source_card()` / `_sync_deck_cards()` / `serve_deck()` 都跳过墓碑身份；
- 专项作答收下答案，返回 `srsApplied=false` 与原因，不重建卡；
- 恢复必须是显式动作并核对墓碑版本；收藏、编辑、内容升级都不撤销删除；
- 无来源的手工卡用 `vocab:<id>` 作为墓碑 source_ref，不留遗漏路径。

删除保留 `lex_review_events` 里的历史，只停止该方向的调度。恢复因此是「重新投放」，
不是「找回旧进度」——旧进度所在的行已经不存在了，声称能找回是骗人。

**决定五：先持久化再发送**

浏览器把操作与会话待发状态写入 IndexedDB 之后才发请求，收到回执后在同一个事务里应用
回执并清除待发标记。408/429/5xx 保留待重试；400/404/409/422 移入 rejected 归档，不再
重放也不阻塞队列，更不显示「已同步」。提示（reveal）与作答共用一条会话内单调 sequence，
因而「准备离线 → 在线看提示 → 离线作答」能重建同一条版本链。

## ADR-LEX-008 —— 查询分页、内容发布与共用个人仓库

**状态**：已签署（2026-09-07，B2–B7 落地）

**决定一：多源查询按同一排序键归并，游标保存各源位置**

排序键冻结为 `(匹配等级, 常用标记, sourceRef)`。教材索引、词典和个人条目各自按它排序，
一个不透明游标记录每个源的偏移。取每源接下来的 `limit+1` 条归并即可产出下一页——再往后
的条目按定义都大于手里的全部，所以跨页无重无漏。

`total` 只在能精确统计时才是精确值；词典候选达到上限时返回 `totalRelation=gte`。把截断数
当总数报出去，比不报更糟：它让「后面没有了」和「后面取不到」变成同一个显示。

筛选一律在分页**之前**做。收藏从完整收藏集反查，而不是过滤已经截断的一页——否则第 131 条
收藏永远查不到。

**决定二：内容发布是一个单元**

`pack.json` 与描述它的每个报告先写入暂存目录并校验，再逐个就位，最后移动 `publish.json`
清单。清单记录 revision 与每个文件的摘要，所以「报告描述的是另一个版本」这件事会被检测
出来，而不是被相信。构建时间只进清单，不进内容哈希。

种子身份由注册表分配，一次分配永不移动。原来按遍历位置编号，在列表前面插一个词就会让
后面每个词换 ID——学习者背了一个月的卡片会全部变成新卡。

**决定三：三个页面共用一份个人卡片副本**

精听、个人中心和词汇页读写同一个 IndexedDB 仓库，通过 `LearningCards` 适配器。每个页面
持有**一个**长期 BroadcastChannel 接收端；每次发送新建一个通道且无人订阅，等于没有广播。
不支持 BroadcastChannel 的浏览器靠 storage / visibilitychange / pageshow 补偿刷新。

合并远端快照前先应用墓碑与待发操作。队列非空时不清理本地缺失的卡：服务端没见过的卡可能
只是还没传上去，删掉就是删掉唯一副本。

条目级笔记（`lex_user_entries.note`）与方向专属提示（`vocab.note`）是两个字段，由
`noteFor()` 统一读取顺序，避免一个页面显示其中一个却保存另一个。

**决定四：撤回的题目保留历史，停止计入**

题目被确认有实质错误后：新会话排除它，活动会话标为 `unavailable` 并允许跳过，已有作答
保留但 `validity='withdrawn'`，错题按仍然有效的事件重算。

已经推进过 SRS 的错误答案不回放。没有后续复习时可以恢复到该次作答之前的状态；有后续
复习时只能记补偿事件——直接回滚会覆盖学习者此后做过的工作。两种情况都先生成建议，由
显式动作决定，不在学习者背后改调度。

## ADR-STUDIO-002 —— 自动化工作台与无人值守流水线规范

**状态**：已签署（2026-09-12）

**决定一：默认无人值守，仅在异常时按问题复核**

传统制课流程要求人工逐句确认与逐页复核，造成大量等待和工作台堆积。
新架构变更为默认无人值守：素材一次性提交 -> 后台异步流水线处理 -> 四值质量门严格评估（`pass` / `fail` / `unknown` / `not_applicable`）-> 通过后自动装入正式课程库/题库。
人工介入转为按需触发：仅在发生隔离阻断、明确缺陷（Issues）或用户显式申请人工复核时才展示工作台，且界面直接定位到具体问题行与差异（Diff）。不再将逐页、逐句手工确认作为上线前置条件。

**决定二：四值质量门与题目自动资格语义**

1. 审核记录绝不伪造人类签名，不批量标记 `verified`。历史已有的 `verified` 仅视为机器结构校验（`machine_checked`）。
2. 开放可靠的机械验证资格：对题型结构清晰且具备确定性答案证据的题型（`reading`、`recall`、`meaning`、`cloze`、`connection`），允许通过 `verification: {status: 'auto_verified', policyId, contentHash, checkRefs}` 获得资格。
3. `contentHash` 必须严格等于题目题面与选项内容的实时散列，一旦题面或答案被修改，资格自动失效（`verification.stale`）。
4. 任何硬性否决（`withdrawn`、`disputed`、`retired` 以及词条 `draft` 状态）具备绝对优先权，不可被任何自动资格绕过。

**决定三：不可变版本与发布资格统一服务**

无论是文件形式（`exam.json` / `pack.json`）还是数据库发布（`/api/v1/admin/publish`），统一切入资格校验服务（`check_exam_qualification` / `check_paper_version_qualification`）。
任一发布入口均强制验证：
1. 试题与选项完整性；
2. 答案证据与非空评分标准（除工作例题外的计分题目必须具备确定正确答案）；
3. 零阻塞性质检错误。
任一入口均无法绕过内容完整性与答案证据检查。
