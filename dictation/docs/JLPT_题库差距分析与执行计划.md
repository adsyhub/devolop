# JLPT 题库差距分析与执行计划

> 审计日期：2026-09-01  
> 需求基线：`docs/题库`  
> 实现基线：当前工作区（包含尚未提交的 JLPT 代码与题库数据）  
> 目的：回答“还有多少功能未吸收”，并给出可分阶段执行、可验收的建设顺序。

## 1. 结论

当前项目已经形成一个可用的**单机 JLPT 真题练习原型**，但还不是需求文档定义的生产级题库系统。

按需求文档第 33 节的 **74 条核心验收项**逐条核验：

| 状态 | 数量 | 含义 |
|---|---:|---|
| 已吸收 | 9 | 当前实现已覆盖核心行为，且有相应代码或测试证据 |
| 部分吸收 | 20 | 有界面或局部能力，但缺服务端规则、数据库约束、恢复能力或完整流程 |
| 未吸收 | 43 | 当前没有对应领域能力，或实现方向与需求相反 |
| 合规豁免 | 2 | 非官方估分未启用；需求允许首版不提供，因此目前不构成缺陷 |
| 合计 | 74 | 与需求第 33 节逐项对应 |

因此，**仍需完善 63 项核心验收能力**，其中 **43 项未吸收、20 项部分吸收**。排除 2 项合规豁免后，严格完成度为 **9 / 72（12.5%）**。

这个数字只统计第 33 节的核心验收项。首页个性化、套卷筛选与详情、内容后台、精读、精听、大模型辅助、性能与运维等第 6～31 节能力在核心清单中没有被完整展开，本文在第 6 节另行列出，不与 63 项重复计数。

## 2. 最重要的判断：当前实现与目标规格存在架构分叉

这不是单纯的页面缺口。

当前 `ADR-EXAM-001` 选择的是：

- 单机自学；
- 与听写播放器同进程；
- SQLite；
- 正确答案随整卷发送到浏览器；
- 浏览器负责倒计时；
- 三种模式：`practice`、`exam`、`review`。

需求基线要求的是：

- 多用户及角色权限；
- PostgreSQL、版本化领域模型和不可变快照；
- 正确答案、解析、脚本在提交前不得到达客户端；
- 严格模考由服务端时间、分科状态机、截止时间和租约决定；
- 内容必须经过来源、许可、答案复核和发布闸门；
- 九种作答模式以及按题组动态组题。

因此，若目标是完整吸收 `docs/题库`，必须先签署一份替代或补充 `ADR-EXAM-001` 的架构决策。继续在现有 `exam_store.py` 和前端内存状态上叠加功能，会把“计时练习”包装成“严格模考”，但无法满足答案隔离、历史快照、多人权限和截止时间的核心约束。

本文后续按“**完整吸收需求，建设生产级模块化单体**”规划。现有导入、审计、题型映射和安全渲染可复用；会话、权限、版本、发布、动态组题与严格模考需要重建。

## 5. 当前实现中的 P0 风险

这些问题不应等待完整重构后才处理。

### P0-1 “计时模考”名称高于真实能力

当前倒计时由浏览器 `Date.now()` 驱动，刷新会丢失，修改本地时间会改变剩余时间，服务端也接受截止后的答案。应立即改名为“计时练习”并提示“不等同严格模考”，直到 E01～E16 达标。

### P0-2 答案隔离方向与需求相反

整卷接口在提交前返回正确答案。它不仅可以从开发者工具读取，Service Worker 还可能缓存整卷。完整吸收需求时必须拆分 Delivery DTO 与 Review DTO，并由服务端权限服务决定答案、解析、脚本和翻译是否可见。

### P0-3 自动保存会提前污染复习状态

`record_answers` 每次自动保存都会调用 `_fold_into_review`。同一场次内先选错再改对，会被计算为一次错题加一次正确复习；严格模式尚未交卷时，复习状态也已经改变。应把“当前答案记录”与“提交后折叠学习状态”分开，只有题组/科目/场次正式提交后才更新掌握状态。

### P0-4 没有历史内容快照

attempt 只记录 `exam_id`、答案和一个结果 JSON，不保存 paper/group/question version。题面或答案更新后，历史作答无法还原当时看到的版本，也无法安全做答案订正。

### P0-5 未完成场次不可恢复

刷新后前端重新初始化，答案 Map、当前位置、deadline 和队列均丢失。数据库虽保留未完成 attempt，但没有恢复入口和状态 DTO。

### P0-6 权利状态不可执行

41 套题中只有 2 套带自由文本权利说明，且说明本身表示未获再分发/销售许可；没有任何一套具有 `APPROVED` 许可。当前数据只能作为用户私有迁移输入，不能作为可发布内容。开发/测试还应改用合成题，避免把真实未授权题目当 fixture。

### P0-7 时长和完整性元数据不可靠

18 套缺场次、18 套缺时长，现有整卷时长也不符合 N1/N2 分科基线。严格模考必须从经过审核的蓝图版本读取每科时间，不能修补当前 `durationSec` 后继续使用整卷倒计时。

### P0-8 提交与保存缺幂等和冲突控制

答案保存没有 Idempotency-Key/answerVersion，重复 `finish` 会改写提交时间，多标签页可相互覆盖。上线前必须引入乐观锁、幂等事件和服务端合法性判断。

## 7. 推荐目标架构

### 7.1 保留什么

- `exam_import.py` 的扫描件导入、跨页拼接和答案数量强校验；
- `exam_schema.py` 中可复用的题面审计规则；
- `PART_KINDS` 的题型语义和前端按 `part.kind` 分组的经验；
- `exam_markup.js` 的安全渲染思想与注入回归测试；
- 原始分报告、错/蒙/跳过区分和复习间隔的产品经验；
- 当前 41 套 JSON 作为**私有、未授权、不可发布**的迁移输入。

### 7.2 重建什么

- 将 `exam.json` 直接作为发布事实源的方式；
- `exam_attempts` / `exam_answers` / `exam_question_state` 三表模型；
- 浏览器 deadline 和单一整卷计时；
- 把正确答案随学习 DTO 下发的 API；
- 客户端加载全部卷子后临时拼专题的组题方式；
- 只有三种模式的会话模型；
- 自动保存即更新错题/SRS 的行为。

### 7.3 推荐形态

首期仍采用模块化单体，但把生产题库与本地播放器原型分层：

```text
导入与迁移层
  现有 Python importer/audit
          ↓
内容与版本层
  Source → License → MaterialVersion → GroupVersion → QuestionVersion → PaperVersion
          ↓
会话与权限层
  PracticeSession → Section → GroupSnapshot → AnswerRecord/Event → ResultSnapshot
          ↓
API /api/v1
  Delivery DTO（无答案） / Review DTO（按权限返回）
          ↓
学习端与管理端
```

若严格遵循需求的默认技术栈，应新建 Next.js + TypeScript + PostgreSQL + Redis + S3 的应用骨架，并让现有 Python 导入器作为 worker/离线工具继续存在。不要先重写导入器；先稳定内容合同和迁移映射。
